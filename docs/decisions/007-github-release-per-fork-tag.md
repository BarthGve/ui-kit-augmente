# ADR 007 — A GitHub Release for each fork publication

- Status: accepted
- Date: 2026-10-15
- Scope: story s60-fork-release

## Context

A `fork@<version>` tag publishes `@barthgve/ui-components` on npm (ADR 005, 006) and nothing else. A consumer cannot see what a version changed, the archive checked by `verify` is only a workflow artifact that expires, and two version numbers coexist without explanation: the package version (`1.4.0-fork.6`) and the product version of the repository (`VERSION`, `0.3.0`). The owner wants a release page per publication. Creating a Release needs write access to the repository contents, which the workflow does not have today (`contents: read`), so the decision is about where that permission goes.

## Decision

1. **A separate `release` job** creates one GitHub Release per `fork@<version>` tag. It has `needs: publish`, the same condition as `publish` (a push on a `fork@*` tag), and `permissions: contents: write` only: no `id-token`. `publish` keeps `contents: read` and `id-token: write`. The job uses the `gh` CLI preinstalled on the runner with the job token (`GH_TOKEN: ${{ github.token }}`): no new action, no secret, no dependency.
2. **Content of the Release**: title `<version>`; marked `--prerelease` (an `x.y.z-fork.N` version is a semver prerelease) and not as the latest; `--verify-tag`; body = a line linking to `https://www.npmjs.com/package/@barthgve/ui-components/v/<version>` placed before the notes generated by GitHub from the merged pull requests (`--notes` with `--generate-notes`); the asset is the `fork-package` archive that `verify` checked, downloaded in the job.
3. **Notes start**: the previous `fork@` tag is the highest other `fork@*` tag by version order (`sort -V`) among the tags of the repository, read through the API (`gh api …/git/matching-refs/tags/fork@`), and passed with `--notes-start-tag`. It comes from tags, not from Releases, so the first Release works: the existing tags `fork@1.4.0-fork.1` to `.6` have no Release. With no other tag, the flag is omitted. The tag is passed to the shell through an `env:` variable, never inlined in a command.
4. **Failure and rerun**: `release` runs after `publish`, so a failure never undoes the npm publication, and nothing in `publish` depends on it. Only the `release` job is rerun (`gh run rerun --job`): a whole-run rerun would replay `publish` on a version that already exists. The job is idempotent: if `gh release view <tag>` succeeds it uploads the archive with `--clobber` instead of creating a second Release, which also repairs a Release created without its asset.
5. **Naming**: the package version `x.y.z-fork.N` identifies the npm package, the `fork@x.y.z-fork.N` tag and the Release. The product version (`VERSION`, `CHANGELOG.md`) is an independent number, tagged `fork-v<VERSION>` (not `v<VERSION>`, a name used by the upstream tags). The install texts say so without writing any number.

## Considered options

- Release step inside `publish` — rejected: it would give `contents: write` to the only job that holds `id-token: write`, the widest privilege on the one job able to publish.
- A third-party release action — rejected: a new dependency on the release path, when the `gh` CLI is already on the runner and does the same in a few lines.
- GitHub Packages as a second registry — rejected: readers need a token even for a public package, and it adds nothing over npm.
- Creating the Release by hand, or from `/dm-release` — rejected: easy to forget, and the tag already is the trigger.
- Notes from the changelog or from changesets — rejected: fork versions are not changeset releases; the generated notes follow the squash titles of the pull requests.
- Marking the Release as the latest — rejected: it is a prerelease version, and the npm `latest` dist-tag already points to it; the GitHub "Latest" badge is only a label.
- Starting the notes from the previous Release — rejected: the first Release has no previous Release; tags exist already.

## Consequences

Easier: each publication has a page with its changes, its npm link and an archive that installs without npm. The `publish` job keeps its permissions unchanged.

Harder: `scripts/publish-fork-workflow.test.mjs` finds the publish job by the words `npm publish` and forbids `id-token` outside it, even in a comment, so the `release` job must contain neither, and the test gains assertions on `needs`, the tag condition, `contents: write`, `--prerelease` and the exists-guard. The `release` job holds write access to the repository: it runs only fixed commands on a tag whose commit passed the ancestor-of-`main` check of `publish`, and takes no untrusted input.

To watch: tags are immutable and a tag publishes to npm, so the first end-to-end proof is the next real publication (the ticket's pull request lists what is unverified). The flags used (`--notes-start-tag`, `--verify-tag`, `--prerelease`) were checked with gh 2.82.1; the runner's version is the one that counts.

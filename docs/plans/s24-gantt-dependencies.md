# Plan — Story s24-gantt-dependencies

Branch: `feature/s24-gantt-dependencies` (framing) · tickets: `feature/s24-gantt-dependencies/<ticket-id>`
Research: `docs/research/s24-gantt-dependencies.md` — read it first; this plan does not repeat it. Design: `docs/designs/s24-gantt-dependencies.md` (+ `.html` mockup): anatomy, states, tokens with contrast, a11y contract, i18n keys, gaps.

## Target story
**As a** project manager **I want** to link tasks by dependencies **so that** I see and respect their order. Complexity 4 in stories.md, **4 after research, at the top of the band** (5 tickets, 10.5 person-days; s23 was 4 with 7.0). Dependency: s23 (merged). Last slice of the PRD's Gantt.
Premises checked against the code: **partly false: "a link needs an overlay layer"** — the clipping is real (`content-visibility: auto` implies paint containment) but an overlay below the rows is hidden and unclickable (opaque row hover background), and one above the rows paints over the sticky task column on horizontal scroll, so it needs a clip that follows `scrollLeft` (t02 proves it first); **false: "SVG sized by tasks x row-height and days x dayWidth"** — `border-width` is a `1px` literal while `row-height` and `day-width` are rem, so a scaled viewBox drifts; geometry is CSS `calc` over unitless day/row custom properties (same as bars); **s22's `onFocus` `index < 0` guard was "dead code" and becomes reachable** (a focusable Remove button inside a row). No new dependency, **no ADR needed** (ADR 005 stays free).

Acceptance criteria (docs/stories.md):
- AC1 A dependency is drawn as a link between the end of one task and the start of another.
- AC2 A dependency can be created and removed by the user, and `onDependencyChange` reports it.
- AC3 A dependency that would create a cycle is refused with a message.
- AC4 Moving a task that has a dependent task shows a conflict when the order would be broken.
- AC5 The dependencies are listed for assistive technology.
- AC6 A Storybook story loads a demonstration data set and lets the user move, resize and link its tasks.

## Lessons carried from s22 and s23 (apply in every ticket)
- Vitest runs `TZ=UTC` suite-wide: any time-zone claim needs a child-process test with a real `TZ`.
- Data-controlled sizes and loops stay bounded (`MAX_LINKS`, a step budget in every search): a mutation that removes a guard must turn a test red, never hang the suite (s23 t01 M9).
- Contrast is tested in all six themes for every new colour pair, with the emitted variables; **stop and report** if an existing token fails (s11 route), do not pick a colour silently.
- Guard tests for unmount and cleanup are written with the feature and proven by mutation (s23 t02 m1, t03: listeners, rAF, scroll listener).
- `useControllableState` has a defect in uncontrolled-with-callback mode: wrap or avoid (avoided here).
- Mutation-test the guards (what the ticket relies on must turn a test red when removed) and report them.
- jsdom has no layout: real pointer, drag, scroll, hit testing, focus and geometry go to Playwright CT (chromium); a premise about layout is a failing-first CT test, not an assumption.
- A dead defensive line that becomes reachable needs its test (the s22 `onFocus` guard).

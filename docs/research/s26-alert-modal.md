## The five structuring facts
1. **The premise "no `role="alertdialog"` in `src/`" is true, and the cause is that `Modal` cannot carry one.** `grep -rn alertdialog src/` finds nothing. `Modal` is built on **react-modal 3.16.3**, not on react-aria (`src/components/modal/index.tsx:3` `import ReactModal from "react-modal"`, rendered at `:152`). `ModalInner` forwards neither `role` nor `aria` to `ReactModal` (`index.tsx:152-168`), so every modal is `role="dialog"` (react-modal default, `node_modules/react-modal/lib/components/Modal.js:240`).
2. **The story's agentic note names a component that does not exist.** `AlertDialog` appears **0 times** in the installed react-aria-components 1.16.0 (`node_modules/react-aria-components/dist/types.d.ts`, `dist/import.mjs`). What exists is `Dialog` with `role` taken from `AriaDialogProps` (`node_modules/@react-aria/dialog/src/useDialog.ts:34`, `role = 'dialog'`, returned in `dialogProps` `:77`), and RAC `Modal` with `isDismissable` (`react-aria-components/src/Modal.tsx:56,96,256`) and `isKeyboardDismissDisabled` (`:97`). **No component in this repo uses RAC `Modal` or `Dialog`**: the overlay engine of every dialog today is react-modal.
3. **react-modal already supports what an alert dialog needs; `Modal` simply does not pass it on.** `role` prop (`ModalPortal.js:385`, default `"dialog"` `Modal.js:240`), `aria` object turned into `aria-*` attributes next to `aria-modal: true` (`ModalPortal.js:387`, `attributesFromObject` `:264-269`), `shouldFocusAfterRender` / `shouldReturnFocusAfterClose` both `true` (`Modal.js:243,246`), a Tab loop through `scopeTab` (`ModalPortal.js:189-190`), Escape through `shouldCloseOnEsc` (`:193-196`), overlay click through `shouldCloseOnOverlayClick` (`:219`). So "alert modal" is **a pre-built variant of `Modal` plus a small additive `Modal` extension** (forward `role`, `aria-labelledby`, `aria-describedby`), not a second overlay engine.
4. **The title cannot name the dialog today, and a naive fix leaves a wrong `aria-label`.** `ModalInner` computes `contentLabel = props["aria-label"] || title?.toString()` (`index.tsx:133-137`) and react-modal writes it as `aria-label` (`ModalPortal.js:386`). A `ReactNode` title (a `<span id>`) gives `"[object Object]"`. `aria-labelledby` wins in the accessible-name computation, so a name-based test would pass and hide it: the change must **skip `contentLabel` when `aria-labelledby` is supplied**, and a test must assert there is no `aria-label` attribute on the alertdialog. The title markup is `div.c__modal__title` holding the icon wrapper and the title (`ModalDefaultLayout.tsx:58-63`), without any id.
5. **The visual of an alert modal already exists: `MessageModal`.** It is `Modal` size `SMALL` + `titleIcon` + one "Ok" button (`MessageModal.tsx:19-47`), with severity icon colours `.modal-message-{error,warning,info,success}-icon` = `content.semantic.<sev>.tertiary` (`modal/_index.scss:119-137`). What it lacks is semantics (role, naming, description), a caller-defined primary action and an accessible icon: its icon is a Material ligature `<span class="material-icons">cancel</span>` **without `aria-hidden`** (`MessageModal.tsx:21-32`), so a screen reader reads the word "cancel". `AlertModal` must hide it.

## Target story
**As a** user of a La Suite application **I want** an alert modal that interrupts me with an important message and asks me to acknowledge or decide **so that** I do not miss a critical warning, error or confirmation. Complexity 2 in `docs/stories.md:457-472`. Acceptance criteria (verbatim intent):
- AC1 `AlertModal` opens as a modal dialog `role="alertdialog"`, named by its title and described by its message (`aria-labelledby`, `aria-describedby`); tested on the rendered DOM.
- AC2 Four severities of `Alert` (`info`, `success`, `warning`, `error`), each with icon and semantic colour read from tokens, no literal colour.
- AC3 Focus moves in on open (to the primary action, or to the dismiss action when there is none), is trapped, and returns to the opener on close.
- AC4 At least one dismiss action; optional primary action; Escape and the dismiss action call `onClose`; outside click does not close by default (opt-in prop).
- AC5 All visible default labels from the five locale files (`yarn check-locales`); title and message caller-provided.
- AC6 `Modal`, `MessageModal`, `ConfirmationModal`, `DeleteConfirmationModal` behave as before (their specs pass unchanged).
Dependencies: none. Agentic notes: build on `Modal`, reuse the severity icons and tokens of `Alert`, keep presentational; shared rules (artifact, one minor changeset, story, tests).

## Traps & constraints
- **Unchanged-surface rule (AC6).** The `Modal` change must be purely additive: no default value moves, `role="dialog"` stays when the new props are absent, `contentLabel` unchanged without `aria-labelledby`. New tests live in **new spec files** (`modal/alert-modal.spec.tsx`, `modal/modal-aria.spec.tsx`) so the diff on `modal/index.spec.tsx` stays empty and a reviewer can check AC6 mechanically.
- **Title/message ids.** The id for `aria-labelledby` must sit on the title **text node only** (a `<span id>` passed as `title`), not on `.c__modal__title` (it would include the decorative icon). `aria-describedby` points at the **message node only**; optional extra content stays outside it.
- **Decorative icon must be `aria-hidden`** (fact 5). Colour is not the sole carrier: the four icon shapes differ and the title carries the meaning.
- **Close X.** Its `aria-label="close"` is hard-coded English; the alert modal uses `hideCloseButton`, the dismiss action is the only close affordance (no new i18n key for it).
- **Standalone means inside a provider.** `Modal` throws without `ModalProvider` (`ModalProvider.tsx:57-62`), and `CunninghamProvider` mounts it (`provider/index.tsx:111`). "Without a provider" is not supported by `Modal` today and AlertModal does not change that.
- **First render.** `Modal` returns `null` on the first render (`index.tsx:106-120`); a modal open by default mounts one tick late. Not a regression, but tests must `await findBy…`.
- **`ModalProvider` surface is public.** Adding `alertModal()` to `ModalContextType` / `ModalProvider` touches a surface the story says stays unchanged; not planned (open question 4).
- **Generated tokens.** If any token is added, `yarn build-theme` regenerates `src/cunningham-tokens.*` and `cunningham-tokens-sass.scss` is known to drift (restore it, apply only the new blocks by hand). The recommended design adds **no token**, so none of this applies.
- **jsdom limits.** `aria-hidden` on the app element and focus return are testable in jsdom (existing spec checks `aria-hidden`); visual claims and the Tab loop in a real browser are checked in Storybook (Playwright + axe).

## Open questions
1. **Focus target on a destructive alert.** AC3 says "to the primary action". WAI-ARIA APG advises focusing the least destructive action for a destructive confirmation. With `severity="error"` and a primary action such as "Delete", Enter-on-open would trigger it. Keep the AC as written (primary), or focus the dismiss action when `severity="error"`? **Needs the owner.** Also: focus behaviour is a **hypothesis** (fact in Verified APIs) until the first red test of t01 runs.
2. **Icon set.** "Reuse the severity icons of `Alert`" is ambiguous: the exported `Alert` wrapper uses SVG icons (and renders `info` with the error icon), `MessageModal` and `AlertIcon` use Material ligatures. Proposed: ligatures via `iconFromType` (consistent with `MessageModal`, no wrong `info` icon, existing `.modal-message-*-icon` colour rules). SVG would need a fix of `INFO` first (outside this story). **Owner to choose.**
3. **Default labels: reuse or dedicated keys.** Proposed: zero new keys. Sole dismiss -> `components.modals.helpers.disclaimer.ok`; dismiss next to a primary action -> `components.modals.helpers.confirmation.cancel`. Alternative: a dedicated `components.modals.alert.{dismiss,cancel}` (2 keys x 5 files). Reuse couples the alert modal to the `helpers` wording; owner to confirm.
4. **Provider helper.** A `useModals().alertModal()` promise helper (like `messageModal`) is plausible but touches the public `ModalContextType` and `ModalProvider`. Not needed by any AC, not planned. Wanted as a follow-up story?
5. **Does a primary action close the modal?** Proposed: no, the caller does (`onClick` then `setIsOpen(false)`), as `Alert.primaryOnClick` does; the dismiss action and Escape call `onClose`. Owner to confirm that the primary action does not auto-call `onClose`.
6. **Real browsers.** Chromium only was installed in previous stories; Safari/VoiceOver announcement of `alertdialog` and the react-aria-free Tab loop are not verified here.

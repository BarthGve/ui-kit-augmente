# Research — Story s23-gantt-move-resize

Worktree `.worktrees/s23-gantt-move-resize`, branch `feature/s23-gantt-move-resize`. Nothing was built or run beyond two throw-away Node snippets (contrast over `cunningham-tokens.css`; `@internationalized/date` month arithmetic). Every other claim comes from reading `packages/ui-components/src/components/gantt/` (merged s22), `components/dnd/`, `hooks/`, and the installed `@dnd-kit/core` 6.3.1 / `modifiers` 9.0.0 / `sortable` 10.0.0 under the main checkout's `node_modules` (read-only).

## The structuring facts
1. **Premise "the s22 scale reserved the pixel-to-date inverse": half false.** s22's research and design promised `positionOf` plus a "one-liner" `dateAt(offsetPx)` / `snap(date, zoom)`. `scale.ts` ships `positionOf`, `dayWidth`, `dayIndex`, `ticks` and `toDay`, but **no inverse, no `snap`, no add-unit helper**. They are all new work (t01). The "one-liner" holds only for day zoom; week and month need calendar rules (fact 6).
2. **`DAY_WIDTH` (px 40/12/4) duplicates the rem tokens** (`2.5rem/0.75rem/0.25rem`) and is only correct at a 16px root font; `Gantt.tsx` already patches that with `px()` = `dayWidth * rootFontSize / 16` for the zoom anchor. A drag must not rely on it. **Measure instead**: `pxPerDay = trackElement.getBoundingClientRect().width / scale.days` (the track is `1fr` of a grid whose width is `task + days x day-width`, so this is exact, whatever the rem, the zoom, a consumer's token override or the 40% task-column cap). The constant stays only for the existing zoom anchor; t01 should not widen its use. jsdom has no layout (`getBoundingClientRect` is 0): the maths takes `pxPerDay` as an argument and is unit-tested pure; the component specs stub the rect.
3. **`MAX_DAYS` windowing affects drag.** The axis is `[origin, end]`, at most 3660 + 37 days, derived from the data (min start, max end, padded to the week/month). Bars are clipped to it (`positionOf`); a task wholly outside has no bar. Consequences: (a) a drag works on the task's **real dates** (never on the clipped geometry); (b) a pointer edit is clamped to the current axis (start >= origin, end <= axis end); a task already touching or crossing the window edge gets a collapsed range and is not pointer-editable (`data-clipped`, no handles); (c) **the axis cannot be extended by dragging**: it only grows after the caller applies a change. Today a user cannot drag the last task past the end of its own week/month. This is the biggest functional limit (open question 2).
4. **Origin shift after a commit.** The axis origin is derived from the earliest start. When a change makes the earliest task start earlier (keyboard, see 3c) or later, `buildScale` returns a different `origin` and every bar jumps horizontally. s22 already has the date-anchor trick for zoom (`anchor` + `useLayoutEffect`); a commit that changes `scale.origin` needs the same (keep the leftmost visible date). New trap, not in s22.
5. **`components/dnd/` and `@dnd-kit` do not fit; native pointer events do. No dependency, no ADR.**
   - `components/dnd/` is two 20-line wrappers (`Draggable` spreads `listeners` + `attributes` and sets `opacity: 0.5`; `Droppable` reports `isOver`). Used only by `tree-view` stories. `attributes` adds `role="button"`, `tabIndex=0`, `aria-roledescription="draggable"`, `aria-describedby`: wrong on an `aria-hidden` bar whose focus unit is the row.
   - `@dnd-kit/core` 6.3.1: `PointerSensor` supports `activationConstraint` (`distance`, `delay`) and cancels on Escape (document `keydown`, `core.cjs.development.js:1453`), `pointercancel`, `Resize`/`VisibilityChange` (`:1450`+). It uses document listeners, **no `setPointerCapture`** (`grep` finds none) and sets `touch-action: none` on the node. `autoScroll` exists and is on by default. Useful, but: (i) `KeyboardSensor` starts on Space/Enter and moves in fixed 25px steps (`defaultKeyboardCoordinateGetter`), `keyboardCodes` are plain `code`s, so **Alt/Shift chords cannot be expressed**; Space/Enter also clash with the row; (ii) there is **no resize concept** (a second draggable per edge, hand-reconciled); (iii) `createSnapModifier(gridSize)` snaps to a **fixed pixel grid**, which is wrong for months (28-31 days); (iv) default announcements are English-only strings (overridable, but then we write them anyway); (v) the result is a `DndContext` + transform, which we would convert back to dates ourselves. We would write the snapping, keyboard, live region, resize and Esc/blur rules regardless; dnd-kit would only supply pointer activation and auto-scroll.
   - **Native pointer events** (~60 lines): `onPointerDown` on the bar/handles -> `setPointerCapture(pointerId)`; `pointermove`/`pointerup`/`pointercancel`/`lostpointercapture` on the same element; document `keydown` (capture) for Escape during the session; `window` `blur` cancels. One code path for mouse, pen and touch. Touch scroll conflict is the real cost (fact 9). Installed and reusable: `react-aria`'s `VisuallyHidden` (direct dependency 3.47.0) for the live region. **Verdict: native pointer events; `components/dnd/` and `@dnd-kit` untouched; no new dependency, so no ADR (next free number stays 005).**
6. **Keyboard model, collisions, and what Escape means.**
   - t04's handler (`Gantt.tsx`, `onKeyDown`) returns early when `altKey || shiftKey || ctrlKey || metaKey`, verified in the code, and a spec loops over the four modifiers (`Gantt.spec.tsx:362`). Alt/Shift+Arrow are therefore free. Plain Up/Down/Home/End keep working unchanged.
   - **Alt+Left / Alt+Right is history back/forward on Windows and Linux** (Chrome, Edge, Firefox). On macOS the browser shortcut is Cmd+Arrow; Option+Arrow does nothing outside text fields (VoiceOver uses Ctrl+Option). So the clash is real off macOS and is solved only by `preventDefault()` on the `keydown`, which browsers honour for these chords as far as known. **Not verifiable here** (no real Windows browser, and Playwright CT cannot assert history navigation reliably): unit test `defaultPrevented`, manual check on Windows/Linux listed as a PR limit. Rule: `preventDefault` only when the chord is actually consumed (editing on, a dated, editable task focused); in read-only the browser keeps its shortcut, as in s22.
   - **Shift+Left/Right** on a non-text row has no browser action; it only extends a text selection, so `preventDefault` is harmless. No keyboard way to move the **start** alone exists in the AC, but start' = move + shorten end composes any pair, so WCAG 2.1.1 holds. Alt+Shift chords are not added (open question).
   - **"Escape cancels a change in progress" implies a session.** If each Alt+Arrow committed at once, there would be nothing to cancel, and a persisting parent would get one write per key press. Proposal: the first Alt/Shift+Arrow opens a **keyboard edit session** (preview, tooltip, live announcement); further presses accumulate **from the original dates** (so Alt+Right then Alt+Left returns exactly to the start, essential for months); **Enter commits** (one `onTaskChange`), **Escape cancels** (original dates announced), losing focus cancels. Needs owner confirmation (open question 1) because the AC wording "Alt+Right moves it by one zoom unit" can be read as immediate.
   - **Escape and ancestors:** an Escape that cancels a session must not also close a surrounding RAC `Modal`/popover: during a session the document `keydown` listener (capture) calls `stopPropagation()` + `preventDefault()`; with no session it does nothing.
7. **Snapping to the zoom unit, calendar semantics** (all on `CalendarDate`, so DST-free, TZ-independent; day counts through `dayIndex` = UTC difference). Verified with `@internationalized/date` 3.12.0: `2026-01-31 + 1 month = 2026-02-28`, `2026-02-28 - 1 month = 2026-01-28` (**clamps, not reversible**), `2024-02-29 + 1 year = 2025-02-28`.
   | Zoom | unit | move by n units | resize end by n units |
   |---|---|---|---|
   | day | 1 day | `start + n days`, same length | `end + n days` |
   | week | 7 days (not "to the next locale week start") | `start + 7n days`, same length | `end + 7n days` |
   | month | 1 calendar month | `start + n months` (clamped), **length in days preserved** | `end + n months` (clamped) |
   - **Delta snapping, not absolute-grid snapping** (recommended; open question 3): a Wednesday-to-Friday task dropped in week zoom stays Wednesday-to-Friday, one week later. Snapping the start to the Monday grid would silently change the start weekday and, in month zoom, move a task starting on the 15th to the 1st on any nudge.
   - **Pointer to units:** day = `round(dx / pxPerDay)`; week = `round(dx / (7 pxPerDay))`; month = nearest of three candidates n0-1..n0+1 (n0 = `round(dxDays / 30.4375)`) by comparing the resulting date's `dayIndex` with the pointer's day: exact at month boundaries, pure and testable.
   - **Always compute from the original dates** (session start), never from the previous preview: dragging out and back returns exactly to the original (month clamp is not reversible incrementally).
   - **End inclusive:** resize clamps `end >= start` (a one-day task has `start == end`, width 1 day). Resize-start clamps `start <= end`. Reaching the clamp is **flagged to the user** (tooltip text + announcement), not silent. Move never changes the duration in days, so move cannot invert.
   - A no-op (net delta 0 units, or clamped back to the original) **does not call `onTaskChange`**.
8. **Controlled component: the preview must not mutate caller data.** `tasks` stays the only truth and is never written. A session holds **transient local state** `{id, mode: "move"|"resize-start"|"resize-end", start, end, unitDelta, clamped}` in `Gantt`; the dragged row renders from it and every other row from `tasks`. Performance: today rows are rendered inline in `Gantt`, so any state change re-renders every row (O(rows)); with 500 rows at pointer-move frequency that is not acceptable. Mitigations: (a) state changes only when the **snapped** delta changes (once per unit, not per pixel; the pointer-follow between snaps is not drawn: the bar jumps unit by unit, which is also what "snaps" means visually); (b) extract the row into a `React.memo` component fed `(task, position, preview?)` so only the dragged row re-renders. The existing `transition` on `inset-inline-start`/`inline-size` (added for zoom) must be **off while a session is active** (`data-editing`), or the bar lags. After a commit the preview is cleared in the same render batch as the caller's new `tasks`; if the caller refuses (no update) the bar returns to its original place (that is the controlled contract; documented).
9. **Touch, pointer cancel, blur.** `touch-action` is evaluated at `touchstart`: a bar with `touch-action: none` drags immediately but **blocks scrolling when a finger starts on a bar** (bars are 20px high in a 40px row, so the track and task cell still scroll). A long-press arming scheme would need non-passive `touchmove` listeners (not pointer events) and is fragile. Proposal v1: `touch-action: none` on the bar and handles only; document it; no long-press. Open question 4. Cancel paths, all restoring the original dates and calling nothing: `pointercancel` (browser takes the gesture, e.g. touch scroll), `lostpointercapture` without `pointerup`, `window` `blur`, `visibilitychange` hidden, Escape. The session ends on first pointer-release path; later `pointermove`s are ignored. A `contextmenu` during a session cancels it. `user-select: none` while editing (prevents text selection while dragging across task names).
10. **Auto-scroll while dragging.** The scroller is one box (sticky column, sticky axis), so dragging near its inline edges (outside the sticky column) must scroll it, otherwise a task cannot be moved beyond the visible window (a 90-day schedule at day zoom is 3600px wide). Proposal: `requestAnimationFrame` loop while the pointer is within 48px of the visible track edge, speed proportional to depth (max ~20px/frame), pointer-to-date recomputed with the **new** `scrollLeft` (dx = clientX delta + scrollLeft delta), stopped at session end; reduced-motion does not forbid it (it is user-driven, not decorative). Kept inside the same ticket as resize/touch (t03). Playwright CT must measure it (jsdom cannot).
11. **Accessibility of the bars.** Bars are `aria-hidden` in s22 and stay so: pointer drag is a pointer feature; **operability is on the row** (the focus unit): `aria-keyshortcuts`, an instruction text via `aria-describedby`, a polite live region for session start / each snapped step (debounced to the settled value) / commit / cancel / limit, and no change of the row's `aria-label` during the session (the live region carries the new dates; a label that changes under focus is noisy). A live region = `role="status"` inside `react-aria`'s `VisuallyHidden`; `@react-aria/live-announcer` is only transitive, not used. Texts are i18n keys in the five locales with `Intl`-formatted dates (design lists them).
12. **Read-only default preserved.** New props `editable?: boolean` (default `false`) and `onTaskChange?`. `editable` without `onTaskChange` is allowed but does nothing observable except previews (documented, dev-only `console.warn`? no: documented only, YAGNI). With `editable` false the DOM, roles, handlers and `preventDefault` behaviour are identical to s22 (spec: snapshot-style equality of attributes; no `aria-keyshortcuts`, no handles, cursor default). An explicit prop beats "editable if `onTaskChange` is given": it reads clearly in a per-screen permission model, and s22 consumers cannot become editable by accident. Per-task `isReadOnly?` was reserved by s22 and is **not** added (open question 6).
13. **Sticky column and scrolling.** The bar lives in `__track`, below the sticky column's `z-index: 1` and the axis `z-index: 2`: a dragged bar passes under them (correct, they are opaque). Pointer coordinates are `clientX`-based; the origin of the track is `trackRect.left` measured at session start and corrected by scroll delta (fact 10), never offset by the sticky column width. RTL: `inset-inline-start` mirrors bars, so the sign of dx would have to flip in `dir="rtl"`; axis RTL mirroring was out of scope in s22, so editing in RTL is **not supported in v1** (open question 5: proposed to force `editable` off in RTL and document it, rather than misbehave).
14. **`content-visibility: auto` clips painting outside the row** (it implies paint containment). A floating tooltip above the bar would be cut. The date tooltip is therefore drawn **inside the dragged row**, beside the bar (design). Rows scrolled out of view while a session runs (auto-scroll, long list) simply stop rendering; the session lives in `Gantt` state, so it survives.
15. **`useControllableState` defect (in uncontrolled-with-callback mode) is not triggered**: this story adds no controllable state (`tasks` is fully controlled, the preview is internal). Do not introduce a hook use for the session.

## Target story
**As a** project manager **I want** to move and resize task bars **so that** I reschedule directly on the chart. Complexity 4. Dependency: s22 (merged). Blocks s24 (dependencies: move shows a conflict; no auto-move of dependents; Storybook demo lets the user move, resize and link). AC (docs/stories.md:399): dragging a bar moves start and end by the same amount and calls `onTaskChange`; dragging an edge changes only that date and a task cannot end before it starts; same changes from the keyboard (Alt+Left/Right move, Shift+Left/Right change end, Escape cancels); drop/resize snaps to the zoom unit; Escape during a drag cancels and restores.

## Traps & constraints
- Month arithmetic clamps and is not reversible: always from original (fact 7).
- Inclusive end: width 1 day at `start == end`; test the boundary and a month-boundary span.
- Never edit `cunningham-tokens.*`; no literal colour/spacing/radius in `index.scss`.
- `parseDate` throws: reuse `toDay`/`spanOf`; a task without a valid span has no bar and is not editable (no bar to grab; keyboard on its row does nothing, announced "no dates" is unchanged).
- `onTaskChange` payload: ISO strings (`"YYYY-MM-DD"`), never `Date`/`CalendarDate` instances, so the caller can store it as it likes (proposal, open question 7).
- Vitest runs `TZ=UTC`: a TZ-independence claim (the edit maths across a DST change) needs a child-process test.
- Data-controlled sizes stay bounded (`MAX_DAYS`): a drag cannot make the axis, ticks or track unbounded; the clamp to the axis guarantees it.
- Contrast is tested in all six themes for every new colour pair.
- Do not break s22 behaviour: all existing Gantt/scale specs stay green untouched.

## Open questions
1. **Keyboard: session with Enter to commit (proposed) or commit on every Alt/Shift+Arrow?** The AC's "Escape cancels a change in progress" needs a session; the first reading of "Alt+Right moves it" is immediate. Confirm; the plan assumes the session.
2. **The axis cannot be extended by editing** (fact 3c). Options: (a) accept in v1 and let s24's demo data have slack; (b) pad the axis with one zoom page on each side in editable mode (changes `buildScale` output, touches s22 expectations); (c) an optional `range` prop (`start`/`end`), additive. Recommendation: (c) as a follow-up story; a heads-up for the owner because "reschedule on the chart" is half-useful without it. Not in this plan.
3. **Delta snapping (proposed) vs snapping the date to the unit grid** (fact 7).
4. **Touch:** `touch-action: none` on bars (proposed) vs long-press arming. Touch cannot be fully tested in Playwright CT (pointer events with `pointerType: "touch"` only); real-device check is a stated limit.
5. **RTL editing:** unsupported in v1 and documented (axis RTL was out of scope in s22). Should `editable` be forced off in `dir="rtl"` so it never misbehaves? Recommendation: yes, forced off with a documented note.
6. **Per-task `isReadOnly?`** (reserved by s22): add now (cheap, additive) or leave to a later need? Recommendation: leave; the caller can render a read-only chart.
7. **`onTaskChange` signature:** `(id, { start, end }) => void` with ISO strings (proposed, as s22's forward note) vs a task-shaped object. Also the payload carries both dates even for a resize of one edge (the caller applies both; avoids partial-update ambiguity).
8. **Alt+Arrow back/forward suppression** cannot be verified on Windows/Linux here: manual check required.
9. **Hit area vs narrow bars:** a bar narrower than ~3 hit targets (month zoom, short tasks) cannot show two 24px handles; resize by pointer is then unavailable at that zoom and the user zooms in or uses the keyboard (design: handles shrink to a third of the bar below 72px, hidden below 24px). Does the owner accept that against WCAG 2.5.8 (24px target; the exception "equivalent control" is arguable)?
10. **Undo:** none (the caller owns the data and may implement it); not in scope.

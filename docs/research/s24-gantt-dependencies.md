## The structuring facts
1. **Premise "links need an overlay layer because rows clip": true for the clipping, incomplete for the layer.**
   - Confirmed from the code: `.c__gantt__row` has `content-visibility: auto` (`index.scss:94`), which implies paint containment, so nothing a row paints leaves its box (s23 research 14 reached the same conclusion for the tooltip). A link from row 2 to row 7 cannot live in a row.
   - **The s23 design note "an SVG overlay can draw over them, `pointer-events: none`" misses two traps**:
     a. *Below the rows* (DOM before the rows with no z-index, as `__today`): the row hover colour is an opaque background on `__track` (`index.scss:97-102`), so the link vanishes in the hovered row, and the track is above it, so the link can never be clicked (selection and removal become impossible).
     b. *Above the rows* (grid child after the rows, `z-index: 1`, below the sticky axis at `2`): each row is its own stacking context (paint containment) and the sticky task cell's `z-index: 1` only counts inside it, so the overlay **paints over the sticky task column once the box is scrolled horizontally**.
   - Decision: the overlay sits above the rows and is clipped to the visible track by `clip-path: inset(0 0 0 var(--gantt-scroll))`, where `--gantt-scroll` is `scroller.scrollLeft` written by one passive `scroll` listener (rAF-throttled, written straight on the overlay element, no React state). First CT test of the drawing ticket: scroll the box 300px, `document.elementFromPoint` at a point of the task column crossed by a link returns the task cell, and a point just right of the column returns the link (falsifiable; if the premise is wrong the ticket's design changes before any other work).
   - Alternative kept in the open questions: draw per-row pieces inside each track (no overlay, no clip, natural hover and sticky behaviour) at the price of one DOM node per row crossed (O(links x rows) instead of O(links)); rejected because a long link then costs one node per row and needs a total-piece budget.
2. **Premise "an SVG sized by tasks x row-height and days x dayWidth" does not survive the tokens.** `row-height` is `2.5rem` and `day-width` is rem, but `border-width` is the literal `1px` (`tokens.ts`). The row pitch is `row-height + border-width` (rows are content-box: the existing `scroll-padding-block-start: calc(row-height + 2 * border-width)` for the axis, two half-height tiers plus two borders, only makes sense that way; t02 asserts it in CT, do not rely on it). A viewBox in px scaled by rem drifts by a fraction of a pixel per row at any root font other than 16px (25 rows at 20px root: more than 6px off), and `DAY_WIDTH` in `scale.ts` is already a documented `ponytail` mirror with the same ceiling. Options: (a) measured geometry (s23 already measures px per day from the track rect), (b) CSS `calc` over unitless custom properties. **Decision: (b)**: each link is a few absolutely positioned boxes (`<div>` segments, 2px lines) placed with `calc(var(--x) * var(--gantt-day-width) + ...)` for x and `calc(var(--y) * (row-height + border-width) + ...)` for y, exactly like bars and the today line. No measurement, no px mirror for alignment, follows any root font size, token override and zoom, tweens with the bars through the same `transition`, and mirrors with logical properties. Arrowheads are the `::after` of the last segment (border triangle: forced-colors safe). Cost: about 3 to 5 nodes per link. Fallback if the CT geometry test cannot reach 1px: measured px geometry in an SVG (document it, do not mix).
   - The only mirror kept is a visual choice, never an alignment: which of two routes to draw (fact 3) uses `DAY_WIDTH[zoom]` and the `link-*` px sizes (ponytail: wrong route at a non-16px root, line still lands on the bars).
3. **How a link is drawn (finish-to-start, no dependency).** Predecessor end = the right edge of its bar (`start + span` days, because `end` is inclusive); successor start = the left edge of its bar. Rows are `tasks` order, so row index = array index (`aria-rowindex - 2`).
   - *Forward route* (gap between the two x is wide enough): stub right from the predecessor end, vertical in the gap at `successor.start - lead`, horizontal into the successor with the arrow.
   - *U route* (gap too narrow, or the successor starts before the predecessor ends, i.e. a conflict): stub right to `end + gutter`, down (or up) to the line between the two rows (the border below row p, or above it), left or right along it to `start - lead`, then vertical to the successor row centre and horizontal into the start. Both routes are orthogonal, at most five segments, pure, unit-testable (`links.ts`).
   - `gutter` clears the connector handle (fact 8): the connector lives at `end + 8px .. end + 32px` (the s23 end handle already reaches 8px past the bar), the vertical segment at `end + 44px` so its 24px hit strip (`+32..+56`) does not overlap it.
   - Cost: O(L) to compute (one pass over valid links, a `Map` id to row index), O(L) nodes; no virtualisation exists (rows rely on `content-visibility`), so the overlay is not skipped off-screen: bounded by `MAX_LINKS` (fact 5).
4. **Clipping by the `MAX_DAYS` window.** `positionOf` clips a bar to the axis and returns null for a task wholly outside. A link whose two ends both have a position is drawn to the **clipped** edge (the real bar edge on screen); a link with an end outside the window or a task without dates is **not drawn but still listed** for assistive technology (with "no dates" / out of window wording from the existing row label). Conflicts are computed on the **real dates**, not the clipped geometry (same rule as s23 editing).
5. **Data model (decided, minimal).**
   ```ts
   export interface GanttDependency { from: string; to: string }   // finish-to-start: `to` starts after `from` ends
   export type GanttDependencyChange = { kind: "add" | "remove"; dependency: GanttDependency };
   // props: dependencies?: GanttDependency[]; onDependencyChange?: (change: GanttDependencyChange) => void
   ```
   - `from` = predecessor id, `to` = successor id (task ids already required stable). **No link id**: the identity of a link is the ordered pair, which is also what `onDependencyChange` reports and what the caller stores (a persistent store assigns its own id). React keys: `${from.length}:${from}${to}`.
   - **No `type`** field: only finish-to-start exists in the story; adding `type?: "finish-to-start"` later is additive. YAGNI now.
   - **Controlled, never mutated** (s23 rule): `dependencies` is the only truth, the callback is the only output, nothing is drawn optimistically. A caller who ignores an `add` sees no link appear (documented, like the snap-back of a refused task move). Reported once per user action.
   - Normalisation (pure, `links.ts`): drop unknown ids, self-links, duplicates (first wins; the reverse pair `B to A` is a different pair), and entries past `MAX_LINKS = 1000` (all data-controlled sizes stay bounded; the rest is neither drawn nor listed, documented in the MDX; an honest gap for a caller with more than 1000 links, open question 5). The input array is never sorted or mutated.
   - Editing affordances (connector, remove, link keyboard session) exist only when **`editable` and `onDependencyChange` are both set**. `dependencies` alone draws read-only links. A s23 consumer (`editable`, no new prop) sees nothing new: **without `dependencies` there is no overlay node at all** (spec: DOM identical to s23).
6. **Cycle detection.** Adding `from to` creates a cycle iff `to` already reaches `from` (or `from === to`). Iterative DFS with an explicit stack and a `visited` set over a `Map<string, string[]>` adjacency: O(V + E), no recursion (a 10 000-link chain must not overflow the stack), terminates on **cyclic input data** (visited set) so a caller's existing cycle can never hang the chart. Kahn is not needed (we never need a full order, only reachability for one new edge). An existing cycle in the data is drawn as given (the component refuses to create one, it does not repair or hide one); its links still get conflict display. Refusal reasons, checked in this order and each with its own message: `exists` (then the same gesture removes, keyboard only), `self`, `no dates` (a task without a bar cannot be linked by the user), `cycle`. The reverse pair (A to B exists, user adds B to A) is a cycle.
7. **Conflict (display only).** FS conflict iff `successor.start <= predecessor.end` (start on the same day as the predecessor ends counts: the inclusive end day is still worked). Open question 2 if the owner wants same-day starts allowed. Computed from **the dates being shown**: tasks, overridden by the s23 session `preview` for the dragged task (`Gantt.tsx` `preview` state: `{id, start, end}`), so a move or a resize shows the conflict live, and after the caller applies the change the conflict stays (it is a property of the data). Nothing moves automatically (story note, run interdict). The link turns dashed + marker + text, never colour alone. Links attached to the dragged bar follow its preview (otherwise they would stay on the ghost).
   - Interplay with s23: `onTaskChange` is untouched and is still called with the dragged task's dates only; the conflict is not a reason to refuse or alter the commit. The live region appends a sentence (`announce_conflict`) to `announce_preview` only when the conflict set changes.
8. **How a user creates a link.**
   - *Pointer*: a **connector** (a 10px dot, 24x24 hit area) at the right end of a dated bar, shown on hover and `focus-within` of the row like the grips, `touch-action: none`. Pointer down on it starts a **link session** (same pattern as s23: pointer capture on the connector, document Escape/blur listeners, `session` ref + local state, nothing else written). While dragging, the row under the pointer is the candidate (hit test by row rects: jsdom specs stub them; CT uses real pointers). A valid candidate shows the prospective link (same renderer, `data-state="creating"`) and its tip ("Start `{name}` after `{from}`"); an invalid one shows `invalid-color` and the reason in the tip; release on a valid row calls `onDependencyChange({kind: "add", ...})` once; release elsewhere, Escape, blur, pointercancel and lost capture cancel with nothing reported. Refusal message is **text in the target row** (tip) + the live region, and stays until the next pointer down, key press or focus change (no timeout: WCAG 2.2.1).
   - *Keyboard* (all pointer functions need a path, 2.1.1): on a focused row, **Alt+Shift+Right** starts a session where this task is the **predecessor**, **Alt+Shift+Left** where it is the **successor**. `onEditKey` returns false today when `altKey === shiftKey` (`Gantt.tsx:629`), so both are free (s23 reserved the single-modifier chords only) and `Alt+Left/Right` history navigation is already handled for the single-Alt case (same `preventDefault` rule: only when consumed). Up/Down (and Home/End) move a **candidate** among the other rows (announced, highlighted, shown as the prospective link), **Enter** applies (adds, or removes if the link already exists), Escape cancels, focus leaving the row cancels. This session sits in front of the s23 branch that cancels and navigates on Up/Down: with no link session those keys behave exactly as before. `aria-keyshortcuts` and the instructions gain the two chords and `Enter`/`Escape` text only when link editing is on.
   - *Touch*: the connector is a pointer target like the end handle (`touch-action: none` on it only); the finger cannot scroll the box while dragging, so a far-away target is reached through the keyboard path or by scrolling first (gap listed, no vertical auto-scroll in this story).
   - Not in scope (open questions): click-to-arm linking (a tap then a tap, which would also satisfy WCAG 2.5.7 for linking), vertical/horizontal auto-scroll while linking, linking to a task whose bar is off-screen by pointer.
9. **How a user removes a link.** *Pointer*: click (or tap) any part of a link (24px hit strip around its middle segments; the two end stubs are excluded so they never steal the connector or the resize handle) selects it (`aria-pressed` is not used: the link layer is `aria-hidden`); a **Remove link** button (24x24, `delete` icon from the existing icon set if one exists, else text glyph; design) appears in the **successor row's track** (a `gridcell`, so a focusable control there is valid ARIA; the overlay is `aria-hidden` and cannot hold one) and takes focus. Enter/Space/Delete/Backspace on it reports `{kind: "remove"}`; Escape or a click elsewhere deselects and returns focus to the predecessor row. *Keyboard*: the same Alt+Shift session; Enter on an existing link's candidate removes it (the announcement says "remove" before Enter). **Carry-over**: a focusable control inside a row makes the `onFocus` `index < 0` guard of s22 reachable; the s22 review (t04) called it dead and unproved (0 mutations red): it needs a test now.
10. **Assistive technology (AC5).** Rows are the focus unit and the label must stay stable during a session (s23 contract), so **no `aria-label` suffix** (the s22 design's extension point is rejected: conflicts change live). Two things, both from the same data:
    - per row: a visually-hidden element referenced by `aria-describedby` (in read-only mode too, appended to the s23 instructions id when both exist): "Starts after: `A`, `B`. Required by: `C`." and the conflict sentence when one applies (`Intl.ListFormat` with the provider locale, at most 5 names then "and N more");
    - one visually-hidden `<ul>` outside the grid (after the scroller, labelled "Dependencies, N"): one item per valid link ("`A` must finish before `B` starts", plus the conflict sentence), so a screen-reader user can read the whole set. It is outside `role="grid"` so no ARIA required-children issue.
    The overlay itself is `aria-hidden="true"` and contains no focusable element.
11. **Contrast (computed from `src/cunningham-tokens.css`, six themes: default, dark, dsfr-light, dsfr-dark, anct-light, anct-dark; WCAG relative luminance; min..max).** Surfaces: `background.surface.secondary` (page), row hover `background.semantic.neutral.tertiary`.
    | Foreground (content.semantic.\*) | on surface.secondary | on row hover |
    |---|---|---|
    | `neutral.secondary` | 6.43..11.86 | 5.65..8.69 |
    | `neutral.primary` | 13.29..15.23 | 9.77..13.41 |
    | `brand.tertiary` | 5.35..7.73 | 4.70..5.66 |
    | `error.tertiary` | 5.37..7.83 | 4.73..5.74 |
    - **Trap: a link over a bar.** The bar fill is `content.brand.tertiary`. Against it `neutral.primary` is 1.73..2.83 (fails), every `*.tertiary` content token is 1.00..1.01 (invisible), `neutral.secondary` 1.20..1.54. **No existing colour is visible on a bar**, so a link crossing one needs a 1px **casing** in `surface.secondary` (which sits at 5.35..7.73 against the fill, the same pair as the s23 grips) under a line that is >= 6.43 against the casing. The design lists the pairs. Same for the conflict colour: it is invisible on a bar, so dashed + marker + text are mandatory, not decorative. If any pair fails in a theme the ticket stops and reports (s11 route).
12. **Forced colors and reduced motion.** The segments use `forced-color-adjust: none` and system colours like the bars (`CanvasText` lines, `Highlight` selected, the marker with `Canvas`/`CanvasText` and a border); the casing becomes `Canvas`. Reduced motion: the `transition` on the segments (they tween with the bars on a zoom change) is removed under `prefers-reduced-motion: reduce`, same rule as `__bar`.
13. **`useControllableState` defect** (uncontrolled-with-callback mode): not triggered, no state is made controllable here (`dependencies` is fully controlled, link selection and the sessions are internal). Do not wrap anything in it.
14. **s23 interplay checked in the code.** A new `Session`-like `LinkSession` shares `listen()` (Escape capture + blur) and the "close first, then act" rule; only one session at a time (`session.current`); a pointer-down on a connector must be ignored while a move/resize session runs and vice versa; the existing delegated `onPointerDown` finds `.c__gantt__bar` with `closest`, so the connector must not be inside the bar (it is a track child) or it would start a move. The roving `stopIndex` effect, `taskRows()` (`:scope > .c__gantt__row`) and the grid `ref` are untouched; the overlay is a grid child **that is not a `.c__gantt__row`** (the selector excludes it).
15. **Demonstration (AC6).** s23 research open question 2 still holds: **the axis cannot be extended by dragging**, so a demo where a user moves tasks needs slack. The data set (a non-exported `demo.ts` module, also mounted by the CT helper so the story and its test cannot drift): 10 to 12 tasks over about three months at week zoom with **about three weeks of free axis after the last task** (add a final dateless-or-short milestone far right), a chain of 5 linked tasks, a diamond (one predecessor, two successors, one join), **one conflict already present in the data**, one task without dates, and a pair that makes the refused-cycle message reachable in two gestures (A to B to C exists: dragging C to A is refused). The story is controlled (`useState` for tasks and dependencies) and shows the last reported change.

## Target story
**As a** project manager **I want** to link tasks by dependencies **so that** I see and respect their order. Dependency: s23 (merged). AC (docs/stories.md:418): AC1 a dependency is drawn between the end of one task and the start of another; AC2 it can be created and removed by the user and `onDependencyChange` reports it; AC3 a cycle is refused with a message; AC4 moving a task that has a dependent shows a conflict when the order would be broken; AC5 dependencies are listed for assistive technology; AC6 a Storybook story loads a demonstration data set and lets the user move, resize and link its tasks (closes the PRD's success criterion "usable in editing mode").

## Traps & constraints
- Overlay: above the rows, `aria-hidden`, clipped to the visible track by the scroll variable, z-index between the rows (auto) and the axis (2); it is not a `.c__gantt__row` and not a child of `role="grid"` semantics (no role, no tab stop).
- `border-width` is a px literal: never size the overlay or any y in rem alone; always `row-height + border-width` pitch from the tokens.
- RTL: editing is forced off in `dir="rtl"` (s23) and the scroll clip assumes ltr: **links are not drawn in RTL** (still listed for AT), documented.
- A `tasks` or `dependencies` array that is huge: `MAX_LINKS` caps drawing and listing; the cycle search is O(V + E) iterative and bounded by that cap plus the task count.
- Month arithmetic and the s23 session are untouched; a conflict never changes `onTaskChange`.
- Vitest runs `TZ=UTC`; conflict maths uses `CalendarDate` and `dayIndex` only (no instant), so a TZ claim still needs a child-process test.
- Contrast in all six themes for every new pair; stop and report if an existing token fails.
- Never edit `src/cunningham-tokens.*` (generated); no literal colour, spacing or radius in `index.scss`.

## Open questions

2. **Conflict rule: `successor.start <= predecessor.end` (same-day start is a conflict) or `<`?** Proposed: `<=`. One line in `links.ts`.
3. **Overlay with scroll clip (proposed) vs per-row pieces** (fact 1). The scroll listener is the price of one node set per link.
4. **Click-to-arm and auto-scroll while linking are out of scope**; the 2.5.7 gap (no single-pointer, non-drag way to create a link) and the far-target gap are listed in the design and the MDX. Do they block acceptance?
5. **`MAX_LINKS = 1000`** with the surplus neither drawn nor listed. Raise, or draw all and cap only the cycle search? Proposed: keep, documented.
6. **No optimistic link**: a caller that applies `add` asynchronously sees the link appear late, with no pending state. Acceptable for V1?
7. **Dependencies to tasks without dates**: the user cannot create them (refused with a message); data-supplied ones are listed, not drawn. Confirm.
8. **Dependency `type` and lag** (start-to-start, lag days) deliberately absent; the PRD says "dependencies" only.
9. **The axis cannot be extended by dragging** (s23 open question 2, still open): the demo works around it with slack; a `range` prop remains a follow-up the owner has not decided.
10. **Links in RTL** are not drawn (see traps).
